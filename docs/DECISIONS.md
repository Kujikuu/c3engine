# Decisions Log

Append-only. Format: date · decision · why.

- 2026-10-18 · Build a new engine in **Rust**, not an editor for the old client · the user wants a general engine ("any game"), like TQ's C3 engine.
- 2026-10-18 · Conquer is a **game module** (`games/conquer`), never part of the engine · keeps the engine reusable for future games.
- 2026-10-18 · TQ formats are **import/export plugins**; the engine has its own native formats · clean engine model + legacy compatibility.
- 2026-10-18 · Location `D:\Conquer2\c3engine`, its own git repo · user choice.
- 2026-10-18 · Planned stack: wgpu, winit, egui, glam, tokio · modern, cross-API, Rust-native.

- 2026-10-18 · Studio UI on **eframe/egui 0.37**; the v1 map viewport draws with egui's painter · fastest path to a usable editor. The game client's renderer (`engine/render`, wgpu) comes later, and the Studio viewport can switch to it then.
- 2026-10-18 · **UI/UX and clean code are standing requirements** · user priority. Studio work is checked with screenshots; the workspace must stay `cargo clippy` clean and `cargo fmt` formatted.

- 2026-10-18 · **Course correction (drift).** Studio work jumped ahead of M1/M2 and edited raw TQ `DMap`s, so the Studio was a Conquer editor rather than an engine editor. Fix, in this order: (1) game-agnostic `engine/scene` + `engine/assets`, plus a TQ importer/exporter; (2) move the Studio onto engine types; (3) finish M1 with the C3 models; (4) M2 wgpu renderer. **Rule: no new Studio features until (1)–(2) are done; editors only ever touch engine types.**
- 2026-10-18 · Engine text is UTF-8. TQ strings are GBK, converted at the importer/exporter boundary (`encoding_rs`). Export→import round-trips are *semantic*: bytes after a fixed-string NUL are not preserved. The raw format parsers stay byte-exact.

- 2026-10-18 · Engine math uses **glam** (`Mat4`, column vectors). TQ/D3D matrices load with `Mat4::from_cols_array` and no conversion (same memory layout).
- 2026-10-18 · Engine animation sampling defaults to the **classic C3 behaviour** (linear matrix blend, matching the original look). SRT/slerp sampling (the client's Enhanced mode) comes later as an option.
- 2026-10-18 · Imported mesh positions are stored **already bound** (bind matrix applied, as the client does). `bind_pose` is kept for a future exporter.

- 2026-10-18 · **The engine never encrypts or obfuscates its own files** (user decision). TQ ciphers (XorRot, the +6 shift, the LevelExp XOR) live only in `formats/c3`: decrypt on import, encrypt only when exporting back to the original 5065 client.
- 2026-10-18 · **Classic meshes draw unlit** (texture × colour), as 5065's graphic.ini disables lighting. The Studio's model view keeps a simple light so shapes read clearly · faithful look in the client.
- 2026-10-18 · Engine blend modes have no destination-alpha factors. The TQ importer maps D3D DESTALPHA→One and INVDESTALPHA→Zero, because the classic back buffer has no alpha channel · ~11% of effects use them.
- 2026-10-18 · Meshes sample with **repeat** addressing (D3D default; effects scroll UVs), sprites with clamp (no seams between ground tiles). Alpha test is 8/255 for all meshes (client ALPHAREF).
- 2026-10-18 · Path finding is **A\*** (octile costs), not the classic greedy best-first search, with the classic step rules (8 directions, not blocked, height difference ≤ 25) and the classic fallback to the nearest reachable cell · shorter, predictable paths; the same cells are reachable.

- 2026-10-18 · **Vision widened (user):** a complete Conquer-like game made entirely in a Unity/UE5-style Studio, as easy as possible, with AI built in. Still C3-style 2.5D games only, no full 3D.
- 2026-10-18 · **AI integration = Studio assistant + MCP** (user choice): a Claude chat panel that edits projects, and an MCP server so external agents (Claude Code) can drive the Studio. Both go through one command layer (`engine/edit`): every edit is a typed, serializable, undoable command. Game AI (behaviour trees, LLM NPCs) and AI asset generation are not planned for now.
- 2026-10-18 · **The engine has its own game server** (user choice), built from the same project as the client. Redux stays usable for Conquer 5065 meanwhile.

- 2026-10-18 · **Saving writes into the project, never the client.** A client map opened in the Studio becomes a project map (`maps/<name>.scene.ron`) on first save; writing back to the 5065 client is an explicit Export (keeps `.bak`). Assets resolve project-first, then the project's content sources, so maps can move into the project before their art does · protects the original client and makes the project the source of truth.
- 2026-10-18 · Native scenes are **RON text + a binary grid sidecar**: readable and diff-able where it matters (objects, portals, layers), compact for the ~1M-cell grids (same 6 bytes/cell as DMap) · a pure-text grid would be tens of MB per map.

- 2026-10-18 · **Assets the Unity way (user):** source files placed in the project's `assets/` folder are used as they are, by importers per file type; nothing is converted. Imported Conquer content is the client's own files (DMap, PUL, ANI, C3, DDS, WDF, ini/dat), and the Studio saves maps straight back to their DMap. This replaces the earlier "save client maps as native scenes in the project" behaviour; the native scene format remains for maps made in the engine.

- 2026-10-18 · **Studio UI stays native egui, styled and laid out like Unity** (user choice over rebuilding it as a Leptos/rust-ui web app): docking panels (Hierarchy, Scene, Game, Inspector, Project, Console) via `egui_dock`, menu bar, Play/Pause/Step toolbar, crafted dark theme, icon set, polished widgets. rust-ui is Leptos (web) only, so it can't render inside egui; its clean look may inspire the theme · keeps the engine viewports native and fast.

- 2026-10-18 · **Roadmap order (user):** finish M3, then M5 (gameplay) and M6 (net + server); AI integration moves from M4 to the end as M8.
- 2026-10-18 · **Scripting is Rhai** (closes the open question): pure Rust (no C toolchain), sandboxed, hot-reloadable, readable for game designers; hot paths (combat, movement) stay in Rust and read data tables · gameplay without recompiling, safe on the server.
- 2026-10-18 · **No ECS library for now** (closes the open question): `engine/game` keeps a typed world (players, monsters, NPCs, ground items in id maps + a cell index) owned by the server simulation; the client mirrors it · an MMO simulation has few entity kinds and benefits more from explicit types than from archetypes.
- 2026-10-18 · **Game data is typed tables** (`engine/data`): a schema (columns with kinds) plus rows, stored readable as `tables/<name>.table.ron`, edited through undoable commands, imported from SQL dumps. The engine framework (`engine/game`) is game-agnostic; a game module supplies its rules (formulas) and the table schemas it reads · data in the project, rules in code, no Conquer in the engine.
- 2026-10-18 · **Simulation owns gameplay, views follow events:** `c3_game::Sim` runs a map in fixed 50 ms ticks and emits events; Play mode (and later the client) shows it through `game_conquer::sim_view::SimView` and reads state for its HUD. The game's `Rules` trait gives monster/item types, base stats and formulas; equipment bonuses are additive and applied by the engine. Conquer's rules read TQ tables; formulas TQ's server is known for are kept, others (dodge, drops) are simplified and marked for M7 parity · the same simulation will run on the server in M6.
- 2026-10-18 · **Game UI is egui (`c3-ui`)**: the in-game UI (HUD, chat, bag, shop, dialogue, overlays) is drawn with egui over the game in both the client (egui-winit + egui-wgpu on the game surface) and the Studio's Game view, styled as game windows; it reads the simulation and returns `UiAction`s for the host. NPC dialogues and shops run in the simulation (server-side later). The Conquer game session and screen (`games/conquer/{session,screen}.rs`) are shared by both hosts · one UI codebase, fast to build; a classic bitmap skin (the 5065/6159 GUI) can come later as a style.
- 2026-10-18 · **Audio is rodio** (pure Rust over cpal/WASAPI, no C toolchain), WAV + MP3 only (the client's formats). The engine plays sounds and music and directs music by region; the game maps its data (ActionSound/MediaEffect/MusicRegion) to sounds for simulation events.
- 2026-10-18 · **Dialogue graphs compile to scripts:** a graph drawn in the Studio is saved as `dialogues/<name>.dialogue.ron` and turned into an ordinary Rhai script (`scripts/dialogue/<name>.rhai`) that NPCs run · one runtime for drawn and written dialogues; the server only ever runs scripts. **Quests** are a table (`tables/quests.table.ron`: goal, target, count, rewards); a player's quest state is script variables (`quest_<id>`, `quest_<id>_kills`), so scripts, the simulation, the UI and saves share it without a separate quest store.
- 2026-10-18 · **Online play mirrors the simulation:** the server runs `Sim`s; each tick it sends every player a `WorldUpdate` of its view (entities within 18 cells that are new or changed, those gone, and the events about them; private events only to their player; others' bags, money and variables stripped). The client applies updates to a mirror `Sim` that never simulates, so the UI, views and audio read it exactly as in offline play. What players do is an `Input` value, handled by `Sim::input` locally and on the server. Messages are serde/postcard over length-prefixed TCP (`c3-net`); a game's original protocol (Conquer 5065) is a separate server front · one gameplay path for offline, Studio and online; the server stays authoritative.
- 2026-10-18 · **Accounts and characters are files** (`<project>/server/accounts/<name>.ron`: salted SHA-256 password hash + `PlayerSave`); unknown names log in by making the account · no database server to install; swap for SQL when a game needs it.
- 2026-10-18 · **The original Conquer client is a front, not a second server:** `games/conquer::protocol::ConquerFront` implements `c3_online::Front` next to the engine's own front, so one `GameServer` (same maps, accounts, saves) serves both clients. It owns the account server (TQ cipher, RC5 password, a one-minute token) and the game server (DH exchange, Blowfish-CFB64), and per client turns each `WorldUpdate` into Conquer packets (spawns, walks, jumps, attacks, attributes, item changes, dialog) and Conquer requests into `Input`s; ids map players to 1,000,000+ and monsters into 400001–599999 · gameplay stays in the simulation; a protocol is only translation.

- 2026-10-18 · **A complete Conquer project comes before more server work** (user, after a review): the import must bring TQ's server data (all maps' NPCs, spawns, portals, tables) with the client content, and the Studio must edit the whole world (maps, NPCs, monsters, items, skills, shops, NPC logic, UI). New M7 "Complete Conquer in the Studio"; prove + ship becomes M8 and AI integration M9, still last.
- 2026-10-18 · **TQ's NPC logic becomes dialogue graphs** (user: "the easier one for the future"): `cq_action` / `cq_task` chains are converted into `dialogues/*.dialogue.ron` graphs rather than ported from Redux's C# NPC classes · they stay editable in the Dialogue editor, and graphs already compile to the scripts the server runs.

- 2026-10-18 · **Correction:** the Studio uses its own dock system (`studio/src/dock.rs`), not `egui_dock`, which doesn't support egui 0.37; the earlier entry naming `egui_dock` was the plan, not what was built.
- 2026-10-18 · **Foundation first (review of the code against VISION.md, asked for by the user):** the apps and the Studio are hard-wired to `game-conquer`, projects have no settings, only TQ art can be used, a world holds one map and rules are Rust code. Roadmap rebuilt: M7 engine foundation (game-module seam, Project Settings, native asset pipeline, multi-map worlds, data-driven gameplay core, undo everywhere), M8 map and world editor, M9 content editors and data-driven game UI, M10 Conquer as a complete project on that engine, M11 any game of the kind, M12 ship, M13 AI (last) · building more Conquer on a Conquer-only base would repeat the drift.
- 2026-10-18 · **Done means done on two projects:** a feature is finished only when it works on a project made from scratch in the Studio (no TQ content) and on the imported Conquer project, checked with screenshots · the earlier milestones were ticked on a four-NPC scratch project.
- 2026-10-18 · **Game rules move toward data and scripts:** the `Rules` trait stays as the engine's seam, but the engine gains a built-in data-driven implementation (tables for stats and formulas as scripts), so a game needs no Rust; Conquer's rules become data and scripts on it in M10.
- 2026-10-18 · **The game-module seam is `c3_play::GameModule`** (M7 step 1): a game gives its assets, `Looks` (a role → an engine `Look` {kind, body, hair, worn items} → a `Character` of models), `GameRules` (the simulation's `Rules` + new characters), maps, sounds and effects; the runtime (world, actors, session, screen, serve) is engine code in `engine/play`. Apps pick the game with `c3-games`; the Studio gets it from `tq_plugin` or falls back to `BasicGame`. Protocol fronts (Conquer 5065) are handed to the server as `c3_online::Front`s, so the engine knows none · one runtime for every game; adding a game is implementing a trait, not forking hosts.
- 2026-10-18 · **The engine draws placeholder art itself** (`builtin:` images: a ground tile and shaded figures, plus a figure model) so a project made from scratch shows a playable world before it has any art; every game's assets answer `builtin:` paths · the Unity "primitive" idea: something to see and move from the first minute.
- 2026-10-18 · **An Input System with actions, devices and platforms (user: "support mobile, pc, mac, xbox, ps controllers"):** new M7 step 3. Game code reads actions, never keys; projects define action maps and bindings per device (keyboard/mouse, gamepads via `gilrs`, touch); the click-to-walk game gets gamepad and touch control schemes; M12 builds desktop and mobile clients. Consoles need the makers' licensed SDKs, so the engine is kept portable for them rather than promising console builds · controls are hard to retrofit once the game UI and screens assume a mouse.
- 2026-10-18 · **Project Settings are one typed file, `settings.toml`** (M7 step 2): `c3_core::settings` holds every section (player, cursors, camera, gameplay, graphics, audio, network, localization) with defaults and rules; a file names only what it changes. A project without the file plays by its game's defaults (`GameModule::default_settings`, so Conquer projects get Conquer's cursors, Silver and the 5065 front). Edits are `c3_edit::SettingsCommand`s (`set`/`reset` a dotted path with a JSON value, checked by round-tripping the typed settings) so the Studio, AI and MCP change settings alike; the Studio saves as it goes · one place for every tunable value, readable and diff-able, AI-editable.
- 2026-10-18 · **Cursors are drawn by the game, not the OS** (the system pointer is hidden over the game view): one path for the client and the Studio's Game view, animated `.ani` cursors on every platform; the engine reads Windows `.cur`/`.ani`/`.ico` itself (`c3_assets::cursor`).
- 2026-10-18 · **Game text uses a `game` font family** (`c3_ui::fonts`): the project's fonts in order, then the defaults; game windows switch to it, so the Studio keeps its own look while the Game view shows the game's fonts.
- 2026-10-18 · **Bindings are text, rebinds are per player** (M7 step 3): a binding reads as `Key Tab`, `Keys W A S D`, `Mouse Wheel`, `Pad West`, `Touch Button`, so `settings.toml` stays readable and AI-editable; the project's `input.bindings` names only the actions it changes from the engine's defaults; a player's rebinds go to `controls.toml` in their config folder (`C3 Games/<game>`) and replace only that device's bindings of the action. The game menu, not the Studio, is where players rebind · the same text works in settings, commands and the menu.
- 2026-10-18 · **Game windows get gamepad navigation through egui's own focus** (M7 step 3): while a window is open, the pad's D-pad/stick become Tab/Shift+Tab and A becomes Enter in the frame's raw input, so every egui widget is pad-usable without per-window code.
- 2026-10-18 · **Assets are used in place with `.meta` sidecars** (M7 step 4): each file of a project's `assets/` gets `<file>.meta` (TOML: a stable id and its importer's settings), as Unity does; the file itself is never converted. Sidecars are written only in the project's own folder, never in a TQ client used in place or copied in. Maps, settings and tables keep naming assets by path; a rename rewrites those paths in the project's text files (quoted `"path"`, `"path/..."`, `"path#..."`), so files stay readable and diff-able while ids survive renames for the tools that need them · readable references, Unity-style identity.
- 2026-10-18 · **Every game plays through `ProjectGame`** (M7 step 4): the project's own assets (images, sheets, glTF, sounds, fonts, `.c3fx`) are layered over the game's content, so a Conquer project can use PNG sprites beside its TQ files and a scratch project needs nothing else. Sub-assets are addressed in the path: a sheet frame `sheet.png#3`, a model texture `model.gltf#texture0`, an effect atlas `fx.c3fx#atlas1` · one path type everywhere, no registry of generated assets.
- 2026-10-18 · **The engine's effect format is readable TOML** (`.c3fx`, M7 step 4): layers of flipbooks (a sheet's animation, packed into an atlas at load) and glTF models, blended additively or by alpha, built into the same `Effect` the TQ importer makes, so the renderer has one effect path · authorable by hand and by AI.
- 2026-10-18 · **Deleted assets go to the project's trash** (`.c3/trash`), so deletion undoes like any other command; renames and deletes wait while the open map has unsaved changes (its scene in memory may name the asset) · nothing is lost to a misclick, no half-renamed references.
- 2026-10-18 · **Hot reload is the Studio's watcher** (notify on `assets/`, settled for 150 ms): changed files and sidecars are read again everywhere they show, including Play; a renamed folder rescans everything · the Import section and paint programs show results at once.
